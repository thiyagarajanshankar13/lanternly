Upgrading Lanternly

An upgrade has two parts: the console on the deployer VM, and clubctl on each services VM when a release changes it. Your services keep running throughout.

#Before you upgrade

  • Read the release notes. They say when servers need the new clubctl, and about any new required setting.
  • Copy /opt/deployer/data somewhere safe (it's small). The console's database is migrated forward on start and can't be migrated back.

#Upgrade the console

#With GitHub Actions

If you use the Deploy the deployer workflow, merge the new release into your copy's main branch. The workflow builds the image and restarts the console.

#By hand

cd lanternly
git pull
sudo docker build -t deployer .
cd /opt/deployer && sudo env DEPLOYER_IMAGE=deployer docker compose up -d

On start, the console applies any new database migrations (they're numbered and only ever added, never edited). Operations that were running when it stopped are picked up again.

#Update clubctl on servers

When the release notes say so, run the setup again on each services VM with the new agent/ folder (same values as the first time), or run the Set up a VM workflow for it. Running containers aren't recreated.

sudo DEPLOYER_PUBLIC_KEY="ssh-ed25519 AAAA… deployer" \
     ACME_EMAIL=you@example.com ./setup-clubs-vm.sh

Servers keep their AGENT_ROOT and AGENT_NAMESPACE from agent.conf, so you don't need to pass them again.

Servers made by the AWS plugin are updated the same way (point the workflow at the server's address).

#Upgrading Ubuntu or Docker

Normal OS updates are fine. For a reboot, the containers restart by themselves. For a bigger change, such as a new Ubuntu release, it's often easier to create a fresh server, restore each service onto it as a copy, move domains and remove the old one.
