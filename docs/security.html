Keep it safe

Security

Lanternly is built so that a compromised console can do as little damage as possible, and so that secrets stay where they belong.

#The console can't get a shell

The console's SSH key is added to the deployer user on each server with a forced command: agent/clubctl-ssh. That wrapper only runs clubctl with a fixed set of commands, each argument checked, and refuses anything else (status; rm -rf / is rejected). The deployer user's sudo rule allows that one program and nothing more.

#Host keys are pinned

Each server's SSH host key is saved when you add it. The console refuses to talk to a server that presents a different key, so a swapped or impersonated server gets nothing.

#Secrets

SecretHow it's kept
App secret settings, registry tokens, bucket keys, SMTP password, GitHub App key, two-step secretsEncrypted with AES-256-GCM under DEPLOYER_SECRET_KEY in the console database.
Database and storage passwordsGenerated on the server and never stored by the console. Reading one is an audited action.
BackupsEncrypted with the backup key before upload. Servers never see the bucket.
LogsSecret settings and anything that looks like a password or token are masked before logs leave the console.
Back up DEPLOYER_SECRET_KEY

It's in /opt/deployer/.env. Without it, the encrypted values in the console database can't be read. Keep a copy in your password manager next to the backup key.

#Sign-in and sessions

  • Everyone needs a password (12+ characters) and an authenticator code. There is no way to turn two-step sign-in off.
  • Sessions are kept on the server and end at once when someone is suspended or removed, or changes their password.
  • Restores and backup key reveals ask for a fresh two-step code, with a limit on wrong tries.

#Access checks

Every server action and admin API route checks the person's access (src/lib/access.ts). A test fails if one forgets. A service someone may not see answers 404, not 403, so its existence doesn't leak.

#Network

  • Databases have no published port. Services in one project can't reach another project's services.
  • Monitoring refuses private and loopback addresses.
  • The GitHub webhook checks GitHub's signature with a constant-time compare.
  • Recommended: allow SSH on services VMs only from the deployer VM.

#Hardening checklist

  • Remove DEPLOYER_SETUP_TOKEN from /opt/deployer/.env after the first sign-in.
  • Limit port 22 on services VMs to the deployer VM's IP; on the deployer VM, to your own IPs.
  • Keep the backup key and DEPLOYER_SECRET_KEY in a password manager.
  • Use a bucket with a different provider from your servers.
  • Give people the lowest role that works, scoped to their projects.
  • Apply OS security updates on the VMs (unattended-upgrades is Ubuntu's default).
  • Upgrade to the newest Lanternly release: only it gets security fixes.

#Report a vulnerability

Please don't open a public issue. Use Report a vulnerability on the repo's Security tab, with what you found, how to reproduce it and what an attacker could do. We aim to answer within 5 working days and fix confirmed problems within 30. Full policy: SECURITY.md.

Out of scope: anything that needs an owner account, root on a VM, problems in the apps you deploy, and denial of service against one install unless it's easy to trigger without signing in.
